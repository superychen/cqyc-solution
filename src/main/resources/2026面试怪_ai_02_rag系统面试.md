# ai rag系统知识相关


### 1、rag的完整流程
    两条流水线：01 索引流水线：文档 -> 加载 -> 切分 -> 向量化 -> 存储到向量库
        02 查询流水线：用户问题 -> 向量化 -> 检索 -> 生成答案

### 2、enbedding是什么？1536维什么意思？
    embedding = 将文本转成向量
    1536维 = 用1536个特征描述这段文本
    embedding是语义的数学表示，用余弦相似度衡量相关性。

### 3、设计一个企业级知识问答系统，怎么设计架构？
    1、架构选型：rag事首选，fine-tuning是补充。 
        01: 知识库是需要频繁更新，rag只需要更新向量库，而微调成本高。
        02: rag可以提供引用溯源，消除幻觉。03: 微调无法处理海量非结构化文档检索。
    2、数据清洗与切片
        01: 切分时不能按字符数。采用markdow语义切分。对于表格这种可以讲表格转为markdown格式，让向量检索时不会丢失行列逻辑。
            给每个chunk增加metadata（元数据），比如文件名、页码、租户、部门。这样检索可以根据权限过滤
    3、检索优化
        01：单次向量检索往往不够，引入multi-query retrieval（将用户问题扩展成多个同义句）和 hybrid search
            （向量检索+关键词BM25检索）来提升召回率。其中rerank重排序环节精选对应top-K进行检索。
        进阶：在工程中还加入redis缓存，将两个用户语义相似问题，第一次进行一个语义缓存，下一次直接从缓存读答案，从而降低token和言辞
    4、评估与工程化
        在后续建立一套ragas评估体系，重点监控四个维度：忠实度、相关度、上下文精度、召回率
    
### 4、如何选择chunk size大小，有什么影响？
    一般256 ～ 512的属于小chunk，优点是检索精确，缺点就是语义可能不完整。适合技术文档和代码。
        512 ～ 1000是我们项目中使用的大小，适中平衡，对于通用文档来说不错。
        1000以上就是大chunk，这种就是语义比较完整，但是对于检索可能不太精准。
    进阶：在rag系统中，我们切分文档是按照根据标题层级切，然后再对于长章节递归切，短章节进行贪心合并，最后添加相关metadata元数据

### 5、如何解决检索结果不相关
    针对提高检索结果，我们系统中使用的混合检索的模式。
    1、首先是 关键词检索 + 多路检索，我们先在查询时提取问题中的关键词，比如商品名，证件名等关键词。然后进行过滤决策。关键词对齐的会
        进行多路检索，模糊的进入候选列表进行用户决策。多路检索通过向量检索 + hyde检索 + 联网搜索 的方式互补，最后通过RRF倒排融合多路结果。
    2、重排序：通过BGE-Reranker精排 + sigmoid归一化。最后选择top-K
    3、优化embedding：如果是向量化的过程感觉不对，可以考虑换更好的模型，BGE-M3中文好。
    4、优化chunking：最后可以尝试调整chunk大小重叠。


### 6、如何降低rag系统的成本？
    1、语义缓存：01:相同/相似问题直接返回缓存，命中率应该有20 ～ 40
    2、prompt压缩：超出限定上下文prompt进行语义摘要，压缩对应prompt。
    3、模型路由：简单问题路由小模型，复杂问题用旗舰模型
    4、优化检索：减少K值（top-K适当调整）。rerank提升精度，减少无效token
    5、批量处理：多个请求合并一个LLM调用。


### 7、如何处理复杂的pdf表格？
    1、使用minerU将pdf转为markdown。对于大量跨页表格，它会自动合并。
    2、并且对于图片通过vLLM记性图片摘要描述，将图片描述进行转换，如果对于vllm识别不了图片层进行OCR识别。

### 8、什么是query改写？如何提升检索效果？ 
    优化用户原始问题，使其更适合检索。
    1、补充上下文。2、查询扩展  3、hyde（假设性文档嵌入）4、多查询生成（将问题拆解成3个子问题）

### 9、什么是上下文压缩？如何减少无效token？
    从检索结果中提取最相关片段，减少llm输入。
    1、上下文压缩是成本优化的关键，我们是用的rerank + LLM提取，从检索的top-K中在用llm提取抽取，从而保证压缩后主要信息不变。

### 10、graphRAg是什么？与普通RAG核心区别？
    GraphRAG = 知识图谱 + RAG，用实体关系图做检索而非纯向量相似度。
    graphRAG用知识图谱替代纯向量存储，核心优势是多跳推理和可解释性。三步：LLM抽取实体关系建图、自然语言转cypher图查询、沿关系路劲推理生成答案。
        系统使用混合方案：向量检索做宽召回，图遍历左精确关系推理。


### 11、Agentic rag是什么，与普通rag区别，如何实现多跳推理？
    agent主动控制检索策略，非被动执行单次检索。
    三种决策来实现：1：信息充分直接回答，2、需要最新信息走实时搜索 3、复杂问题先分解在分别检索。核心是agent每轮评估信息是否足够回答问题，
        不够就继续检索，最多3轮避免无限循环。


### 12、rag效果不好如何排查和提升？
    判断问题：
        1、是检索没找到相关内容，这种属于召回问题。需要判断是embedding模型问题，还是chunk切分的大小有问题，或者查询和文档表达不一致？
        2、找到了但是排序靠后，排序问题，看下rerank重排序，是否生效。
        3、找到了但是模型没用上，生成问题，这种就看下context上下文是太长，或者提示词没有引导好，需要优化下提示词。最后再看是不是模型能力不足。
    总之按照分三层诊断：召回层（混合检索+query改写）、排序层（BGE-Reranker精排）、生成层（上下文压缩+prompt优化）


### 13、rag出现幻觉怎么办？
    三层防护：1）prompt层约束模型只能引用context内容，未找到时主动说无法回答； 2）低temperature（0.1 ～ 0.2）让模型保守生成
        3）ragas faithfulness指标持续监控，评分0.7以下回答标记为低置信度并转人工。

### 14、如何建立rag系统的生产级可观测体系？
    总共有三个层级：检索层看召回率+chunk覆盖率，生成层看faithfulness + 回答情况，系统层看TTFT+成本。我们用的langsmith做的链路追踪，
        每次rag调用记录检索多少chunks、用了多少tokens，最终失败率是多少。从而来提升系统的稳定性。

### 15、如何处理文档版本更新？
    1、用redis做版本控制：在redis中记录每个版本的完整信息（包括版本好、时间戳、chunks快照）
    2、milvus只存最新：milvus中始终保留最新版本数据，检索不需要版本过滤
    3、先插后删：新版本插入milvus，成功后再删除旧版本，避免数据丢失
    4、支持回滚：从redis中取出历史版本快照，重新导入milvus中。

### 15、rerank模型怎么选？
    cross-encoder（精度之王）
    我们项目用的是rrf粗排召回对应top10,然后用BGE-reranker精排top-3.从实际上看，准确率提升至88%左右，代价就是多了2～3秒的延迟
        并且有了额外的开销。

### 16、RRF融合原理？
    RRF (Reciprocal Rank Fusion) 是倒数排名融合算法。

    公式：score(d) = Σ weight_i / (k + rank_i(d))

    d 是待评分的文档
    i 是第 i 路检索
    weight_i 是第 i 路的权重
    rank_i(d) 是文档 d 在第 i 路中的排名
    k 是平滑参数，通常设为 60
    优势：
    1、不需要考虑不同检索结果的分数分布差异  2、算法简单，计算高效  3、对异常值不敏感
    答：在我们的项目中，向量检索和 HyDE 检索权重都是 1.0，联网搜索权重是 0.5。越靠前的排名加分越多。

### 17、企业级rag多租户隔离以及数据权限设计？
    可以设计为四层防线
    1、租户隔离：每个租户的数据都是隔离开的，不可跨租户检索
    2、部门/角色过滤，同一租户内，只有特定角色可见
    3、文档级粒度权限：某些文档只对个人和小组开放
    4、查询级过滤：检索时动态注入权限条件
    

### 18、Transformer是什么，为什么要引入？
    Transformer 通过自注意力机制替代了RNN的串行计算。每个token可以关注所有其他token，实现并行计算，训练速度是10 - 100倍，虽然复杂度是O(n²)，
        但在实际应用中，并行带来的收益远大于复杂度的损失

### 19、RAGAS 的四个指标是什么？如何优化？
    Faithfulness（忠实度）：答案是否基于检索内容，合格线：> 0.7。 Answer Relevance（答案相关性）：答案是否回答问题，合格线：> 0.8。
    Context Relevance（上下文相关性）：检索内容是否有用，合格线：> 0.8。Context Recall（上下文召回率）：是否检索到了正确答案，合格性：> 0.8


### 20、如何用 LLMLingua 压缩 Prompt？能省多少成本？
    我在 RAG 系统中集成了 LLMLingua，把检索回来的 5000 字参考资料压缩到 500 字，Token 成本降低 90%。关键是压缩后的文本语义完整，
        LLM 依然能准确回答问题。对于高频调用的场景，这个优化非常值得。

### 21、RAG 项目上线后怎么治理？检索策略灰度发布、效果评测、回滚怎么做？
    我们生产配置是；策略配置中心化热加载，top_k和混合检索权重改配置不重启。上线后走灰度发布 Shadow（影子）→Canary（金丝雀）→全量三步灰度。
        Shadow 模式新策略影子运行只记录不生效，Canary 放 5% 真实流量验证，通过后全量。质量评估通过recall召回率和faithfulness进行线上收集评估，
        如果发现问题，可根据配置一键回滚。根据线上的异常请求回答进行单独优化。
