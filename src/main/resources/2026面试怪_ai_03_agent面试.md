# agent面试题


### 1、ReAct 模式是什么？完整流程是什么？
    ReAct = Reasoning + Acting（推理 + 行动）
    1. Thought（思考）：分析当前情况，决定下一步
    2. Action（行动）：调用工具（搜索、API、数据库等）
    3. Observation（观察）：获取工具返回结果
    4. 循环 1-3，直到任务完成
    5. Final Answer（最终答案）

### 2、 Function Calling 的原理是什么？
    让 LLM 调用外部函数。本质是将非结构化的自然语言转化为结构化的 JSON。在实战中，我通过它实现了自然语言直接查询 SQL 数据库，极大地降低了非技术人员的使用门槛


### 3、如何防止 Agent 进入死循环？
    死循环原因：1、工具调用失败，agent重复尝试。2、任务太复杂，agent无法完成 3、prompt设计不好，agent理解错误。
    防护措施：1、最大轮次限制（最后10伦） 2、超时机制（超60s后停止） 3、工具调用去重 4、反思机制 5、人工介入

### 4、多 Agent 协作怎么设计？
    整体供应链agent中包括采购寻源协同agent、食品安全agent、主数据agent。从新品引入到原料配比、以及证件核验的agent系统。

### 5、你设计过哪些类型的 Agent？
    基于供应商协同agent: 可以理解为供应商在接入协同前后的问答操作系统，在供应商意向合作界面时可进行问答以及合作意向。
    在供应商入驻后，可通过问答获取订货通知单、合同、证件等相关问题，以及报表。
    食安、主数据agent：在供应链系统中，提供食品安全证件自校验，订单证件原料物料bom信息质量合规。并且在主数据新品引入、供应商引入等模块分析可接入商品，参与自动审核，自动下单，智能补货


### 6、Agent 的 Memory 怎么设计？
    短期记忆 和 长期记忆
    短期记忆：1、存储最近N轮对话 2、用列表或环形缓冲区 3、超出限制时总结或截断
    长期记忆：1、存储重要信息到向量数据库 2、按需检索相关记忆 3、支持遗忘机制，删除历史记忆

注意：1、谈agent时不要只说agent会调用工具，要这样说：我认为agent的核心在于闭环。模型生成答案后，我会设计一个review节点让它自我检查，这个答案是否满足用户需求？如果不满足则重新执行。这种反思机制可提升agent的可靠性。
    2、谈function calling时不要说只调用外部api，要这样说：function calling的本质是将非结构化的自然语言转换为结构化json。比如通过自然语言直接查询sql数据库，降低非技术人员使用门槛。同时加入鉴权机制和黑白名单保证安全性。

### 7、什么是LangGraph?如何构建复杂Agent工作流?
    用图结构构建有状态的Agent应用
    LangGraph解决了LangChain的痛点:不支持循环和复杂分支。我们系统是用LangGraph构建了多Agent,支持多轮迭代优化,从开始到结束,循环直到质量达标。,比纯Prompt灵活。

### 8、工具调用的完整流程，如何处理失败？
    工具调用流程，识别->参数提取 -> 执行 -> 结果处理

### 9、工具调用失败如何处理？充实策略是什么？
    工具调用失败分三类处理：1、参数错误（这种可以让llm重试，或手动更正）、
    2、因调用方突然服务问题导致api瞬时调用错误，然后在某一时间恢复，可能多agent因为积压的请求可能会导致瞬间打死，这种解决方案加入重试时间，抖动请求，比如协同agent实在0.3s内进行重试，食安agent可以在1.5s后进行重试。把请求分散到0~2秒内随机。
    3、然后对于如果重试5次之后，仍然失败，则进行熔断。在配合half-open半打开试探机制，进行重连服务，从而保护后端服务。

### 10、Agent 的短期、长期与工作记忆如何实现读写、检索和遗忘？
    记忆系统 = agent的大脑存储，决定能否长期陪伴用户。
    短期记忆设计: 1、滑动窗口 2、 分层管理(推荐⭐)：比如三轮对话内保留完整对话记录，历史的对话进行摘要处理。
    长期记忆设计：1、向量数据库，存用户偏好和事实，用LLM判断重要性决定是否存储。检索时混合向量+元数据过滤，避免无关记忆。

### 11、 Agent 如何做规划（Planning）？任务分解策略是什么？
    把大任务分解成可执行的小步骤
    Agent规划我用Plan-and-Execute,先用LLM制定完整计划,再逐步执行并根据结果调整。复杂任务用Tree of Thoughts探索多路径,每层生成3个候选思路,评分选最优。工具调用多时用ReWOO预规划+批量并行,比ReAct快40%。关键是要能动态调整计划,而不是死板执行。
    cluade中提出的自适应思考，让模型自动判断何时需要深度推理、何时快速响应

### 12、单轮对话和多轮对话的 Token 消耗大概多少？如何控制？
    单轮对话 Token 消耗约 1K-4K，多轮不控制会线性增长爆成本。我的策略是三层：最近3轮保原文保障连贯性，历史部分用小模型摘要（节省80%成本），RAG 召回内容做相关性过滤只保留 top-k chunk。实测10轮对话 Token 消耗控制在 2K 以内，单次成本 < ¥0.01。

### 13、agent的上下文窗口管理有哪些策略，如何避免超出限制？
    上下文管理是 Agent 落地的关键工程问题。我的策略是分层记忆：短期保留完整上下文，中期用摘要，长期用向量检索。
        对于工具返回，我会在传入 LLM 前先做裁剪和摘要，避免无效 Token 消耗。

### 14、Anthropic 的“可信 Agent”框架是什么？为什么 Agent = Model + Harness + Tools + Environment？
    Agent 不是单一技术，而是四个组件的系统工程：Model 提供智能，Harness 提供约束，Tools 扩展能力，Environment 定义边界。
        任何一环出问题都会导致 Agent 不可信。我在面试时会强调：'我不是在选一个最强模型，而是在设计一个可信的系统'——这正是 2026 年企业级 Agent 岗位的核心要求

### 15、Workflow、Agent 和 Tools 三者的区别与联系是什么？
    ools 是原子能力，Workflow 是固定编排，Agent 是动态决策。区别的关键是'谁控制流程'：Workflow 是代码控制，Agent 是 LLM 控制。
        生产中我会混用——Agent 决定做什么，Workflow 负责怎么做某个固定步骤。比如客服 Agent 决定'需要查订单'，然后调一个固定的查询 Workflow 返回结果。

### 16、什么是 Guardrails（安全护栏）？如何在 Agent 中设计输入输出安全防护？
    Guardrails 是生产 Agent 的安全底线，分输入和输出两层。输入层防注入攻击、脱敏 PII、过滤离题；
    输出层检测幻觉、过滤有害内容、校验格式。我会用 Guardrails AI 框架，配合 Pydantic Schema 做输出格式验证——
        LLM 输出不合格时自动 re-ask 重试，大幅减少人工处理异常输出的成本。关键原则是'深度防御'，不依赖单一检查，多层叠加

### 17、如何防御prompt注入攻击？有哪些具体防御措施？
    prompt注入是agent常见安全威胁，攻击者可以在文档里埋指令，等 Agent 检索时执行。可以在系统中设置防御六件套：
        1、xml标签隔离用户输入 2、正则清洗注入模式 3、系统末尾提示重申安全边界 4、输出检测防系统提示泄露
        5、llm-as-judage二次验证 6、rag文档也要做注入检测。

### 18、Agent 的核心架构公式是什么？决策引擎、信息视野、执行通道分别是什么？
    Agent 不是更聪明的聊天机器人，而是'决策引擎+信息视野+执行通道'的闭环系统。决策引擎是LLM负责想，信息视野是上下文负责看，
        执行通道是工具负责做。agent是能通过工具改变系统状态，并且循环迭代直到完成任务--本质上它是大模型与真实业务系统的软件接口。

### 19、Harness 工程是什么？为什么说“模型决定上限、Harness 决定下限”？
    Harness（马具）= Agent 系统的中间件层 + 治理层，把业务通用的能力抽出来统一封装
    模型调用只占 Agent 系统代码量的不到 20%，剩下 80% 都是围绕模型的工程层——这就是 Harness
    harness工程包括：1、上下文管理（决定每次调用放什么信息：历史截断，知识召回，冗余压缩，记忆维护）
        2、工具调度（工具注册/发现/调用/重试/熔断，动态加载、并行调度）3、约束与验证（输入过滤、权限验证、输出审查、风险评级）
        4、可观测性（轨迹日志，性能指标，成本统计，失败归因）

### 20、 千轮上下文关联怎么实现？对话摘要算法具体怎么做？
    痛点：1、token爆炸（全量上下文飙升） 2、长下文遗忘：模型对早期信息lost in the middle 3、检索困难（历史信息太多，无法快速定位）
    方案：短期 + 长期分层管理
    分层摘要算法（核心答案）：第一层：轮次摘要（每 3-5 轮对话 → LLM 压缩成一段摘要）第二层：会话总摘要（多段轮次摘要 → 再压缩成会话总摘要）
            存储：摘要进向量库（可检索）+ 短期原文在内存/Redis
    召回机制（不是全量塞）：用户提问 → 向量检索相关历史摘要（Top3-5）+ 最近对话原文（固定窗口）+ 结构化实体（用户偏好/资质信息）→ 拼装上下文

### 21、SKILL.md 是一次性全塞进 context 的吗？Progressive Disclosure（渐进式批漏） 三级加载机制是什么？
    SKILL.md 不是全量加载的，Progressive Disclosure（渐进式批漏） 三级机制：metadata 常驻（每个约 100 token），正文按 description 语义匹配按需加载，
        资源文件由模型主动用工具读取。

### 22、 Agent 上下文管理有没有系统性框架？Write/Select/Compress/Isolate 四象限是什么？
    Select > Write > Compress > Isolate**——选择先于写入，压缩是保底，隔离最谨慎
    上下文管理 2026 年的标准框架是 Write/Select/Compress/Isolate 四象限，窗口再大也要管，因为 n² 注意力导致长上下文能力退化。
        性价比最高的是 Select——渐进式披露，先目录后正文按需加。压缩是保底不是越多越好，目标是最小化整个任务的总 token 而不是单次；隔离最谨慎，防上下文污染

### 23、LangGraph 如何实现失败重试、中断恢复和人工介入
    LangGraph 的生产级能力我讲三个：重试、恢复、人工介入。重试是节点级容错，重试失败走兜底分支，但工具调用必须幂等；恢复靠 checkpointer 状态快照，
        每个节点执行完就存一次，进程挂了用 thread_id 从断点续跑，快照同时就是执行轨迹；人工介入用 interrupt 暂停高风险步骤，人类确认后 Command(resume) 继续。


### 24、Agent 并行工具调用怎么做？如何处理混合成功失败的情况？
    并行工具调用的核心不是技术上能不能并行，而是'该不该并行'。我的决策流程是先画工具间的依赖图——有依赖就串行，无依赖评估成本和限频后再决定是否并行。
        LangGraph 天然支持 fan-out/fan-in 模式，但我会在并行前加一个 cost filter，比如航班搜索便宜可以先查，如果航班的搜索结果已经足够回答用户问题，
        就不需要再并行查酒店了。混合成败的处理关键是宁可返回部分结果并说明缺失情况，也绝不伪造数据。

### 25、AI Agent 的观测性（Observability）怎么落地？有哪些关键指标？
    三层可观测性体系：1、Trace（追踪，LangSmith：每一次执行的完整路径）2、Metrics（指标，Prometheus + Grafana，成功率、耗时分布、token 消耗）
        3、Eval（评测，RAGAS，输出质量是否达标）

### 26、如何防止 AI 应用生成有害内容？
    内容安全应做纵深防御：输入分类、权限与策略、受控生成、专用输出审核、人工升级和审计。让生成模型自检可以作为弱信号，
        但同源模型可能重复同一错误，不能当独立安全边界；各层要在代表性与对抗数据上分别测漏放率、误拦率和延迟

### 27、如何处理用户隐私数据？
    PII 治理不仅是正则脱敏：还要做数据盘点与分级、最小化收集、合法处理依据、访问控制、加密、保留/删除策略、供应商与跨境评估。
        正则适合部分格式化标识，还需实体识别和业务规则

### 28、如何对 LLM API 做限流和熔断？Token 速率控制和背压机制怎么做？
    为什么要限流：按token计费、调用延迟高。如果qps过高，比如1000的qps，但是gpt模型api限制只有400 ～ 500。所以肯定会高
    方案：我的实现用令牌桶控制 TPM，配额用 OpenAI 的 90% 作为安全水位。兜底后如果超过该水位的请求还在持续进来，则超过后进行拒绝。不让用户等待，
        不然等待过程中会更容易让系统崩溃。

### 29、Agent 在生产环境中常见的内存泄漏有哪几种？如何排查和修复？
    在生产环境中，我主要排查泄漏点有三个：第一是语义缓存没有TTL和最大条目限制，几千个活跃回话就把缓存称爆。第二个是在第一版设计记忆设计的时候，在对于长期记忆设置，
        没有做好压缩摘要，导致长期记忆膨胀。第三个是在异步处理消费任务中，因为没有做好生产端和消费端正常速率匹配，导致消费没有生产快，队列积压导致内存泄漏。
