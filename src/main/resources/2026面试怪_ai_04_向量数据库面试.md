# 向量数据库

### 1、向量数据库有哪些索引？分别有什么区别和原理？
    1、HNSW: 原理：多层图结构，贪心搜索。优点：01、在合适参数和数据分布下通常有很好的低延迟表现。02、精度最高 03、支持实时插入。 案例：Milvus
    2、IVF：倒排文件索引。聚类 + 分桶搜索。优点：01、内存占用适中 02、适合大数据量 03、构建速度快。 案例：FAISS
    3、IVF-PQ(乘积量化)。优点：01、内存占用极低。02、适合超大数据量。03、检索速度快。  4、LSH（局部敏感哈希） 5、Flat（暴力搜索）

### 2、混合检索的融合策略有哪些？RRF 算法详解
    1、混合检索 = BM25(关键词) + Vector Search(语义)
    为什么需要融合？：BM25精确匹配关键词，会漏掉同义词。向量检索：找到语义相关词语，理解同义词。混合检索：精确+语义双重保障
    融合策略对比：
        1. 加权线性组合：公式：final_score = α * vector_score + (1-α) * bm25_score。 缺点：归一化复杂，易受异常值影响。
        2、RRF：思想：只看排名，不看分数。公式：RRF_score(doc) = Σ [1 / (k + rank_i(doc))]
            - rank_i(doc): 文档在第i个检索器中的排名  - k: 平滑常数(通常k=60)
            优势：01、无需归一化。02、不受异常分数影响 03、参数少（只有K需要调） 04、工程简单
        2、加权RRF
    答：RRF只使用各路排序名次，不要求不同检索器的分数同尺度，因此是稳健基线；公式中的常数K控制头部名次差异，60是常见示例而非通用最优值。
        应在带有关键词、语义和过滤场景的标注集上，与加权分数融合。

### 3、为什么需要两阶段检索？（向量检索 + rerank）
    单阶段：问题：向量检索用"整体相似度"，可能遗漏细粒度匹配
    两阶段：优势：粗排用向量快召回，精排用模型保精度。
    两阶段检索是生产环境的标配。向量检索负责粗排——快速从1000万条里召回100条；Rerank负责精排——用Cross-Encoder对100条重新打分排序。

### 4、HNSW 生产调参实战：M/ef/efConstruction 如何选择？有哪些性能陷阱？
    HNSW 调参主要看 M、efConstruction 和 efSearch：M 影响图连边、内存与构建成本，efConstruction 影响建图质量，efSearch 在查询时权衡召回与延迟。
        不存在跨数据集的黄金值；要固定过滤条件和目标 Recall，在真实向量分布及并发下画 recall-latency-memory 曲线。

### 5、什么是向量数据库的“混合搜索”？为什么重要？
    **混合搜索 = 向量检索 + 标量过滤 + 关键词检索 融合**
    当查询同时包含语义、精确词项或结构化条件时，混合检索和元数据过滤值得评估；但不是所有场景都必须混合。选数据库时应检查过滤是在 ANN 前、中还是后执行，
        以及过滤选择性对召回和延迟的影响，而不是只比较表达式语法

### 6、如何监控与调优向量索引？HNSW/IVF 各有什么指标？
    原因：RAG 系统的检索质量直接由向量索引决定，但向量索引的监控长期被忽视。传统监控只看 API 延迟，却无法区分"检索慢"是索引问题、网络问题还是模型问题。
    HNSW 生产监控四大黄金指标：1、P99 检索延迟，延迟>30ms，调大M/ef，或切diskANN 2、Recall@K（召回率），<85%时，调高efConstruction
        3、内存使用率，>85%，降维或量化 4、索引构建时间，>N * 30min，并行构建或减少数据

    | 追求精度 | 32   | 128  | 200  | 慢但准     |
    | -------- | ---- | ---- | ---- | ---------- |
    | 追求速度 | 8    | 32   | 100  | 快但召回降 |
    | 平衡模式 | 16   | 64   | 128  | 默认推荐   |

    答：向量索引的监控有三个层次：基础设施层（CPU/内存/磁盘IO）、索引层（召回率/延迟/内存占用）、业务层（检索满意度）。
        我们用Prometheus监控内存+延迟，然后在看api延迟，并且看对应的四大指标，P99检索延迟，召回率，内存使用率来动态调整M/ef/efConstruction等参数

### 7、什么是 Context Poisoning（上下文污染）？RAG 知识库如何防御？
    Context Poisoning 是 RAG 的供应链攻击——把恶意文档注入知识库，让 RAG 检索到错误内容生成错误答案。防御四层：来源白名单（写入时验证）
        → LLM-as-Judge 内容审核 → 向量异常检测（偏离知识库整体分布的向量要警惕）→ 检索结果运行时过滤。对自动爬取的知识库尤其要注意间接投毒，建议爬取内容先进人工审核队列再入库。
