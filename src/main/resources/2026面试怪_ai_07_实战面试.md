### 1、你们agent是怎么拆的？：按角色、按业务、按工具权限、还是按任务粒度？
    1、重点是按业务职责来进行拆分的，里面用角色明确责任，按照工具权限落实边界，任务细粒度交给编排层处理。
    2、在csx各个业务部门中业务数据，规则以及对应操作权限都是不一样的，所以是按照业务层级去拆的，我主要负责采购、食安、主数据、合同这四个
        agent，采购agent主要负责的是采购需求、询比价、采购订单等，主数据agent主要负责核对商品、供应商、品牌、地点档案等辅助建档变更等。
        食安agent主要负责的是证件要求、核验结果、原料匹配建议。合同agent主要负责的是合同差异比对，合同起草等。
    3、这样按照业务拆分之后，每个agent都有明确的输入输出、可用工具和完成条件。例如，主数据agent辅助建档中，会校验商品编码、地点等相应字段是否可用，
        是否有缺失资料等。每个agent都有自己的边界职责。这样的粒度能保证独立的业务，专业的上下文以及工具边界。

### 2、supervisor / orchestrator agent怎么派活，子agent结果怎么会和，失败子任务怎么处理？
    1、首先：Multi-Agent System的核心角色： 
        编排者 / 规划者（Orchestrator / Planner / Supervisor）：系统的“大脑”与管理者，主要就是接收用户输入，将复杂任务进行拆分子任务，将子任务拆分分发给下面每一个专用agent。
        专项执行者（Specialized Agent / Executor）：系统的“干活主力”
        评审者 / 验证者（Reviewer / Critic / Evaluator）：负责检查前序 Agent 输出结果的准确性、完整性、逻辑连贯性以及是否符合安全标准
        汇总者 / 综合者（Summarizer / Synthesizer）：在各个专项 Agent 和评审流程结束后，将分散的中间结果、数据或多方观点进行提炼、整合与结构化，形成统一且连贯的最终答案反馈给用户
        交互代理 / 用户代理（User Proxy Agent）：：系统与真实用户之间的“桥梁”或代表。负责接收用户的初始指令、在需要人类介入（Human-in-the-loop）时请求用户确认或补充信息，并将系统执行状态反馈到前端界面
    2、主要考点：按什么依据派任务、结果怎么合并、失败后如何继续？
        01、按什么依据派任务：planner规划者中主要负责理解目标、拆任务和整理方案；然后通过harness负责工具权限、执行限制和任务记录；langgraph表达依赖和状态流转。
            如果说采购要采用一批商品，这个时候主数据agent会确认商品、供应商和地点。然后采购agent、食安agent并行获取相对应的有效报价，证件要求，
            最后在根据方案、确认后正式下单。
        02、结果怎么合并：先是子任务agent先拿到目标、输入、和调用的工具后，执行相应任务，任务完成后结构化对应结果，返回task ID、版本号、业务对象实体、处理状态、以及相关时间等。
            最后在协调层就是汇总者将中间结果数据进行提炼返回最终答案。
        03、中途失败怎么处理：1、如果工具调用问题、或者网络问题以及短暂技术性故障，会尝试对应的次数重试。2、如果是缺什么资料、或者需要hunman in the loop的问题暂停
            并向用户进行提问；3、业务拒绝则返回到底是哪里阻断；4、写操作后如果结果一直超时，则先查执行结果，不能直接重试。
            5、已完成的结果进行保留，如果系统恢复后通过thread id继续执行。

### 3、langgraph的state、Node、edge、checkpointer你们生产怎么用、断点恢复怎么落？
    state是保存业务状态，node执行具体步骤，edge是控制流转，checkpointer保存可恢复状态。
    1、我们系统中state定义成结构化业务字段。比如采购任务会保存 采购需求、商品及供应商编码、主数据校验结果、食安校验结果等业务状态。
    这样planner判断下一步就可以明确字段，不必猜执行到哪里。
    2、对于主agent来说，子agent其实就是一个node，对子agent来说，还可以拆分其他的节点，采购agent里面我拆分了报价、生单、审批等相关节点。
    3、edge使用我们一般固定顺序用普通edge；需要结果分支用条件edge。比如在商品供应商没匹配成功，那么就进入商品建档、供应商建档；食安和合同可以并行。
    4、checkpoint：保存图的进度，我们用的持久化存储，一个流程中是绑定了一个稳定的thread_id。重启后根据thredid找回执行状态到哪一个节点继续执行。
    断点恢复这一块主要分为人工审核 以及 执行故障：
        人工审核：比如商品新建后，在独立节点人工审核调用interrupt，然后将id、版本、内容返回确认。然后通过相同的thread id调用command恢复流程。如果中途内容发生变动，
        比如价格、商品变动，则需重新发起。
        执行故障：恢复服务根据任务记录找到原来的 thread_id，读取检查点，继续尚未完成的任务。

### 4、agent跑到第7步崩溃，前面已经发了邮件或者建了工单了，怎么保证恢复时不重复发、不重复建？
    我们不会只依赖langgraph的checkpointer保证不重复。如果外部系统已经发出邮件创建工单，和本地保存检查点之间存在时间差：外部操作成功，服务没有记录直接崩溃。
    恢复后节点就可能继续执行，所以我们生成一个全局业务操作id，类似于skywalking记录的traceid，并且持久化，在通过下游幂等或者查询处理重新处理。


### 5、工具调用幂等怎么做：创建订单、扣费、发消息这种有副作用操作和只读查询怎么分开？
    我们在工具注册时就区分只读和有副作用的操作，两类工具采用不同的权限、重试和恢复策略。分类是由服务端进行决定的，而不是让模型自己定义。
        查询商品、供应商属于只读，可以超时后进行重试。写操作如创建工单，发邮件等副作用场景，需要经过参数校验，权限检查，并且通过全局id保证一致性。
        并且写操作遇见超时，先判断是否已经成功。

### 6、tool超时，返回空，返回部分成功，返回500，这四种情况agent分别怎么处理？
    我们会同时看工具类型、业务返回协议和实际执行状态，不会只根据 HTTP 状态码决定是否重试。 
    对只读工具，主要判断结果是否可用；对写工具，首先确认有没有产生业务影响。
    
### 7、怎么防止agent死循环，最大步数、反思节点、人工介入、状态不变终止这些机制怎么组合？
    1、死循环的处理：我们在harness层记录节点执行、工具调用和业务状态变化。如果agent连续调用同一个工具，参数和结果基本相同，任务缺没有实际推进，就判断疑似循环。
        就比如采购调用查商品，一直查同一个商品，始终返回多个候选，不走下一步确认规格，就会被拦截。进入反思节点判断是向用户补充提问还是直接停止任务。
    2、最大步数：这个要看图的最大执行步数，以及业务执行时的预算。图层级防止节点无限流转；业务层去限制具体的调用次数、模型调用次数，总耗时和成本。
    3、反思节点：我们是在失败或者连续重试时触发反思，并限制反思次数。输入当前目标、最近调用记录、错误信息和已有结果，输出明确判断下一步应该做什么。
    4、人工介入怎么处理：当系统需要人判断，或者无法安全继续时，就暂定任务。商品候选无法确定，还有合同模版供应商存在冲突等，这种就需要人工处理。
    5、状态不变终止怎么处理：我们都是关注业务字段是否变化，不是聊天有没有变长。商品是否确定，证件是否核验、合同是否匹配，订单状态是否明确。
        如果连续若干次执行后，关键字段还没变化，就粗发停滞处理。
    6、怎么组合？每次执行前先检查剩余预算，执行后检查任务是否完成、是否阻塞，以及有没有有效进展。有进展就继续，没有进展就进行有限反思。
        有可执行的新方案才继续，否则转人工或者结束。这套方案最大步数负责兜底，状态检测负责提前发现问题，反思负责有限纠偏，人工介入负责处理系统无法自行解决的问题。
        
### 8、prompt injection怎么防？用户上传的文档、网页抓取内容、工具返回文本都可能投毒
    首先我们对于用户侧包括上传的文档，网页、文字都是按照不可信数据处理。他们提供业务数据，但是绝对不能修改系统规则，授予权限也不能直接授权工具执行。
    然后对于提示词注入，如用户上传文档在解析阶段对隐藏文字、异常控制符、可疑指令进行一定检测，对可疑文档可进行隔离，然后在检索时按用户权限分类，防止数据错乱。
        比如在用户上传的时候说该证件已经审核通过，这种只能作为待核实信息，最终审核状态还是由食安系统进行判断。还有在工具层限制访问范围，
        如果信息让系统将内部数据比如采购价格、供应商信息传入外部网络中，这种限制就能有效避免。
        还有工具返回数据，用结构化数据，然后通过pydanyic校验，保证不返回自由文本内容。
    当然模型不可能识别所有投毒文本，在设计的时候，就要考虑模型即使被误导，外部内容也要受权限，操作要进行鉴权，业务数据要经过校验。


### 9、工具权限怎么做，普通用户、内部运营、管理员能调的tool集合一样吗？
    不一样，会根据用户身份、角色、数据范围和当前任务，动态提供允许的使用的工具。模型只能看到当前任务需要的工具，真正执行时，还会有鉴权操作，
        避免模型直接绕过限制调用。

### 10、rag答非所问，你怎么判断是召回错了、rerank排歪了、上下文截断了，还是模型没用检索结果？
    我们是按照召回候选 -> 重排结果 -> 最终上下文 -> 生成答案 逐层检查。每次请求保留同一个traceid，记录各阶段的文档id、分数、顺序和实际输入，
        定位正确证据在哪一层丢失，或者被错误使用。
    如何判断召回错误？检查重排之前的候选集合，看正确证据有没有检索出来，如果不在，就判断是在召回层。
    如何判断rerank排歪了？正确证据在初始候选中，但rerank排名明显下降，最后没进入候选阶段。
    怎么判断上下文截断：正确证据已经排进选取范围，但最终发送给模型上下文中没有，或者只剩下一段。
    怎么判断模型没用检索结果？正确、完整且适用的证据已经进入最终上下文，但答案仍然与证据不符，就排查生成阶段。做两次对照，只提供问题和正确证据，看回答是否正确。
        逐步加入历史消息和其他片段，看从哪里答偏。

### 11、hybrid search 里BM25和向量怎么融合，RRF和cross- encoder reank你们用哪种，成本怎么样
    BM25是适合那种精确词匹配，比如协同问答中，匹配精确证件名称，商品编码等精确词汇。向量检索就是根据语义找到能够匹配度较高的文档。
    然后通过混合检索的方式先走精确匹配，然后在向量检索召回，最后通过rrf进行融合。我们项目中使用的稀疏向量+稠密向量的混合检索。我们通过
    业务评测集评测完成之后，在协同文档平台，权重是稀疏0.3，稠密0.7。最后在增减rerank进行重排最终返回top5,来增加检索可信度。

### 12、embedding模型要换，五千万向量怎么迁移，不停机，不降召，能回滚，具体怎么做？
    我会采用新旧索引蓝绿迁移：旧链路继续服务，新模型重新计算五千万条向量，通过全量回填增加增量同步追平，在做影子验证和灰度切流。
        回滚窗口保留旧模型，旧索引和增量更新。不降召回需要通过评测级和线上指标验证，不能因为迁移完成就保证，不达标旧不切，或保留新旧双路检索。
    怎么迁？从权威的原始文本或切片存储重新生成向量，不能把旧向量直接当作新模型输入。
    迁移期间如果新增、删除怎么搞？从快照对应的日志位点开始，持续消费文档变更，分别更新新旧索引。采用可靠事件日志和独立消费进度，避免请求里同步写两套系统，一边成功一边失败却无法补偿。
    怎么保证召回不下降？先做离线评测，再做线上影子流量。旧链路正常返回答案，新链路后台检索，两边使用各自的模型编码同一个问题。

### 13、agent单次任务成本涨了3倍，你从token、工具调用次数、重试、rerank、上下文膨胀那几个点查？
    1、先确认成本统计口径，在对单个任务进行拆分，对比涨价前后同类任务，找出到底是增加了哪一步导致成本突然飙升。重点看的就是token，调用次数，重试，检索重排，
        以及上下文随步骤增长情况。
    2、对于任务来说，是真的变贵了，还是任务变了，如简单任务问答减少，复杂的采购任务增加，这种成本增加是正常的，还需要关注底层模型是不是更换，计费单价是否变更，
        缓存命中率是不是降低。
    3、在看token用量。如果是token数量不变，查缓存，如果上下文暴涨，就查上下文，查规划，反思，回答长度这些是否有变化。
    4、工具调用次数：是不是重复在调用。

### 14、说一个你们线上最难的agent bad case，根因，止血，长期修复分别是什么？
    之前最开始主数据agent的一个故障吧，采购报价完之后，供应商，主数据agent的一个商品变更环节。采购agent已经发起商品变更，主数据agent此时超时，
        采购agent没拿到变更号，工具层统一返回的是失败，agent此时就重新规划再次提交，实际已经生成单子了，最后导致的重复变更单。
    根因：最开始的一版返回协议不完整，幂等控制只是在单agent中，多agent时全局唯一标识当时主数据agent未绑定同一业务。编排层没有写恢复路径，规划层收到失败直接就是重复下单。
    止血：关闭商品变更单据下单入口，已生成单据不允许继续下单，同时筛查受影响任务，补状态任务，重复单据筛选出来业务人员处理。
    长期修复：把工具结果拆成成功、明确失败和结果未知，LangGraph 根据结构化状态路由。结果未知只能进入查单或人工核查，不能回到自由规划重新提交。
        其次，整个链路生成一个全局唯一的操作id，在重试、消息重投、断点恢复都沿用这个 ID，下游在创建订单的事务里完成幂等校验
        最后，保存操作记录以及外部单号，恢复时能查对应的业务结果，在决定是不是进行下一步。
